STACK: Next.js App Router + TypeScript on Cloudflare Workers via @opennextjs/cloudflare; D1 (SQLite) through getCloudflareContext().env.DB; no ORM, prepared statements only. UI language Vietnamese. Money = integer VND (đồng), never decimals, shown like "120.000đ".
TRANSPORT: JSON over HTTP under /api, camelCase fields, UTF-8. Auth = HttpOnly cookie `sid` (SameSite=Lax, Path=/, Secure in prod, 30 days). Every route except register/login requires auth.
SUCCESS ENVELOPE: HTTP 200 (201 on create) `{"ok":true,"data":{...}}`; `data` is ALWAYS an object (never bare array/null); empty result = `{}`.
ERROR ENVELOPE: `{"ok":false,"error":{"code":"<CODE>","message":"<Vietnamese text>"}}`, CODE → status: UNAUTHORIZED 401, FORBIDDEN 403, NOT_FOUND 404, VALIDATION 400, CONFLICT 409, RATE_LIMITED 429, INTERNAL 500. RATE_LIMITED also sends a `Retry-After` header (seconds). Group missing → NOT_FOUND; caller not an active member → FORBIDDEN.
TYPES (lib/types.ts is SSOT):
- User {id, username, displayName, role: "user"|"admin", createdAt, bank: BankInfo|null (the caller's OWN profile account)}
- AdminUserRef {id, username, displayName, createdAt}
- AdminUser = AdminUserRef + {bannedAt: string|null, banReason: string|null, recentAbuse: number (spam violations in the last 24h)}   (listed to the admin; plain users only)
- AdminGroup {id, name, inviteCode, memberCount, expenseCount, createdAt, deletedAt: string|null}
- IpBan {ip, reason, source: "admin"|"auto", createdAt, expiresAt: string|null (null = until lifted)}
- IpSuspect {ip, accounts (distinct accounts), events, lastAt}
- Group {id, name, inviteCode, memberCount, myMemberId, createdAt}
- BankInfo {bin (6-digit NAPAS BIN), accountNo (6..19 digits), accountName (1..50 chars, trimmed)}; a bank profile is all three set or `null`
- Member {id, groupId, name, userId: string|null, username: string|null, removedAt: string|null, createdAt, bank: BankInfo|null, isOwner: boolean}   (bank is DERIVED from the linked user's profile, so always null when userId is null; isOwner = member.userId equals groups.created_by)
- Viewer {userId, memberId: string|null, isOwner, isAdmin}   (the caller relative to ONE group; the admin account has memberId null, isAdmin true, and counts as owner-level everywhere)
- ExpenseShare {memberId, amount}
- ExpenseKind = "expense"|"payment"
- Expense {id, groupId, title, amount, paidByMemberId, spentAt, note: string|null, shares: ExpenseShare[], kind: ExpenseKind, createdByUserId, createdAt, updatedAt}
- LogEntry {id, groupId, actorUserId, actorName, action, entityType, entityId, summary, detail: object|null, createdAt}
- Balance {memberId, name, removed: boolean, paid, owed, net}   (net = paid - owed; >0 means should receive)
- Transfer {fromMemberId, toMemberId, amount}
- StatsPeriod = "all"|"year"|"month"
- StatsBucket {key, label, amount (integer VND), count (number of expenses)}
- StatsMember {memberId, name, removed: boolean, owed, paid}
- GroupStats {period, year: number|null (null when period = "all"), month: number|null (1..12, only when period = "month"), total (integer VND), count, buckets: StatsBucket[], members: StatsMember[]}
- Preset {id, groupId, name, unitPrice (integer VND per unit), createdAt, updatedAt}
- LogAction = "group.create"|"member.add"|"member.join"|"member.remove"|"member.bank"|"expense.create"|"expense.update"|"expense.delete"|"preset.create"|"preset.update"|"preset.delete"|"preset.sync"|"group.rename"|"group.delete"|"group.restore"; LogEntityType = "group"|"member"|"expense"|"preset"
IDs are UUID v4 strings (LogEntry.id = decimal string of an autoincrement integer). Timestamps ISO 8601 UTC with ms, e.g. "2026-10-15T08:30:00.000Z".
ENDPOINTS:
- POST /api/auth/register {username, displayName, password} → 201 {user}, sets cookie. username 3-32 chars [a-z0-9_.] (lowercased), displayName 1-50, password ≥ 6. Taken → 409 CONFLICT.
- POST /api/auth/login {username, password} → {user}, sets cookie; bad creds → 401 UNAUTHORIZED.
- POST /api/auth/logout → {} ; GET /api/auth/me → {user} or 401.
- PUT /api/profile/bank {bank: BankInfo|null} → {user: User}. Always acts on the CALLER's own row; there is no id parameter, so a member can never set anyone else's account (the old `PATCH /api/groups/:groupId/members/:memberId` is REMOVED — that route keeps only DELETE). `null` clears the profile. Invalid body → 400 VALIDATION via `parseBankInfo`; the admin account → 403 FORBIDDEN. No activity-log row: profile data is not group-scoped.
- GET /api/groups → {groups: Group[]} (groups the caller is an active member of); POST /api/groups {name 1-60} → 201 {group} (creates group + creator member named after displayName + invite code).
- POST /api/groups/join {inviteCode} → {group}; idempotent if already a member.
- GET /api/groups/:groupId → {group, members: Member[], viewer: Viewer}.
- GET /api/groups/:groupId/members → {members: Member[], viewer: Viewer} (includes removed ones, removedAt set). POST /api/groups/:groupId/members → 201 {member}, body is EXACTLY one of {name} (friend without account) or {username} (link a registered account; name defaults to their displayName); name 1-50, unique among active members case-insensitively (409), unknown username 404; open to every active member. DELETE /api/groups/:groupId/members/:memberId → {} soft delete (sets removedAt); the owner can never be removed (any caller, the admin included → 409 CONFLICT OWNER_PROTECTED); the owner and the admin may remove anyone else; a plain member may remove only their own row (leaving the group); everything else → 403 FORBIDDEN. A member with no linked account has `bank: null` everywhere.
- GET /api/groups/:groupId/expenses → {expenses: Expense[], members: Member[], hasMore: boolean, viewer: Viewer} non-deleted, spentAt desc, capped at the 300 newest (hasMore=true when older ones exist; `members` equals GET /api/groups/:groupId so the list page needs one request). POST same path {title 1-100, amount int 1..1e12, paidByMemberId, participantMemberIds: string[] (≥1), spentAt?: ISO (default now), note?: string|null, kind?: "expense"|"payment" (default "expense")} → 201 {expense}. A "payment" (settlement transfer: payer paidByMemberId paid `amount` to the single receiver named in participantMemberIds) must have EXACTLY one participant and it must differ from paidByMemberId, else 400 VALIDATION; it is stored as an ordinary paid/share row, so the settlement endpoint cancels that debt with no extra logic; recording one also requires PERMISSIONS.canRecordPayment (403 FORBIDDEN for a member who is neither party). GET/PUT/DELETE /api/groups/:groupId/expenses/:expenseId → {expense} / {expense} (same body as POST) / {} (soft delete); PUT/DELETE require PERMISSIONS.canModifyExpense (403 FORBIDDEN otherwise). `kind` is IMMUTABLE: PUT keeps the stored kind (a body kind is ignored) but a payment still must satisfy the one-receiver rule; the log action stays expense.create/update/delete.
- ADMIN (one dedicated account, role "admin", created only by scripts/create-admin.mjs; registration always yields role "user" and rejects the reserved names admin, administrator, quantri, root, support). Every /api/admin/* route: 401 without a session, 403 for a non-admin, and reachable from a banned IP (the admin can never be locked out). Every action writes an `admin_audit` row in the same batch (never a password).
  ACCOUNTS: GET /api/admin/users → {users: AdminUser[]} plain accounts, newest first, max 500. POST /api/admin/users/:userId/reset-password {password?: string 6..128 (untrimmed); absent or "" generates a 12-char random one} → {user: AdminUserRef, password: string, generated: boolean}: the plaintext is returned ONCE and never stored or logged; the hash is replaced and ALL of the user's sessions are deleted (audit "password.reset"; shares the stricter "auth" rate limit; 404 unknown id, 403 admin target). POST /api/admin/users/:userId/ban {reason?: string ≤200} → {}: sets banned_at/ban_reason, deletes every session (signed out at once), audit "user.ban"; data is kept; 403 for an admin target, 404 unknown. POST /api/admin/users/:userId/unban → {} (audit "user.unban"). A banned account cannot log in (403 FORBIDDEN, only after the password verified; a wrong password is still 401) and its session never authenticates.
  IPS: GET /api/admin/ip-bans → {bans: IpBan[] (active only, ≤200), suspects: IpSuspect[] (abuse in the last 24h, not banned, ≤20)}. POST /api/admin/ip-bans {ip, reason?: ≤200, hours?: int 1..8760 (absent or null = permanent)} → 201 {ban: IpBan}; ip is validated and normalised (IPv4/IPv6; 400 otherwise); banning the address the admin is calling from → 400. DELETE /api/admin/ip-bans?ip=… → {} (idempotent). Audit "ip.ban"/"ip.unban".
  GROUPS: GET /api/admin/groups → {groups: AdminGroup[]} (deleted included, newest first, ≤200). PUT /api/admin/groups/:groupId {name 1..60} → {group: {id, name}} (log "group.rename" with detail {before:{name}, after:{name}}). POST /api/admin/groups/:groupId/delete → {} soft delete (sets groups.deleted_at; log "group.delete"); POST …/restore → {} (log "group.restore"); both idempotent and write no log row when nothing changes; 404 unknown group. The log rows carry actorName "Quản trị viên".
  ADMIN AS GROUP ACTOR: every existing /api/groups/:groupId/* route works for the admin without membership (view and edit expenses, members, presets, log, settlement, including a deleted group). It acts as a built-in actor `{id: "admin:<userId>", name: "Quản trị viên"}`, so each change is logged under that name, and its `Viewer` is `{memberId: null, isAdmin: true}` — owner-level by PERMISSIONS, except that the group owner's member row is still protected from removal. The admin is still never a member row: GET/POST /api/groups and POST /api/groups/join return 403 for it, it is not in any members list, and it cannot be linked by username (404). GET /api/groups/:groupId returns myMemberId "" for it.
  SOFT-DELETED GROUPS: a deleted group is 404 for members on every route, is omitted from GET /api/groups, and its invite code no longer joins (404). Nothing is erased.
- PRESETS (a named unit price used as an alternative way to fill an expense amount; an expense stores only its title and total, so presets never affect history):
  GET /api/groups/:groupId/presets → {presets: Preset[]} sorted by name A-Z. POST same path {name 1-50, unitPrice int 1..1e9} → 201 {preset}; name unique per group case-insensitively and Vietnamese-aware (409 CONFLICT); max 100 per group (400 VALIDATION). PUT /api/groups/:groupId/presets/:presetId {name, unitPrice} → {preset} (404 if the id is not in this group). DELETE same path → {} (hard delete).
  POST /api/groups/:groupId/presets/sync {sourceGroupId, overwrite?: boolean (default false)} → {added, updated, skipped, presets: Preset[]}. Copies the source group's presets into this group. The caller must be an active member of BOTH groups (403/404 otherwise); sourceGroupId equal to :groupId → 400. A name already present is skipped; with overwrite=true only its PRICE is taken from the source (the target keeps its own name). Nothing is ever deleted. Past the 100 cap → 400 and nothing changes. A sync that changes nothing writes no log row.
- GET /api/groups/:groupId/log?limit=&before= → {entries: LogEntry[], nextBefore: string|null} newest first, limit default 50 max 200, before = LogEntry.id cursor.
- GET /api/groups/:groupId/settlement → {balances: Balance[], transfers: Transfer[], totalSpent: number, viewer: Viewer}. `balances`/`transfers` count every non-deleted row, payments included (that is how a recorded transfer cancels a debt); `totalSpent` sums `kind = "expense"` rows only, so payments are never counted as spending.
- GET /api/groups/:groupId/stats?period=all|year|month&year=YYYY&month=1..12 → {stats: GroupStats}. Spending charts. Defaults: period=all; for year/month the year defaults to the current year and the month to the current month, both in Vietnam time. Invalid period, year outside 1970..2100 (a year is 4 digits, so `26` is rejected) or month outside 1..12 → 400 VALIDATION; a malformed year/month is rejected even when the period makes it unused. Only non-deleted `kind = "expense"` rows count — a settlement payment is never spending — and `total`/`count` cover the whole range.
  TIME ZONE: Asia/Ho_Chi_Minh is a fixed UTC+7 with no DST, so a row's local instant is `spent_at + 7h` and a period is a local calendar range. `spent_at` is canonical ISO UTC, so the bounds compare as text.
  BUCKETS: period=all → one bucket per local year that HAS data, ascending, key/label "2026", no zero fill. period=year → exactly 12 buckets, key "01".."12", label "T1".."T12", zero-filled. period=month → one bucket per day of that local month (28..31), key "01".."31", label "1".."31", zero-filled. `amount` sums the expenses in the bucket, `count` counts them. Keys are what the SQL groups by (`strftime('%Y'|'%m'|'%d', datetime(spent_at, '+7 hours'))`); `lib/stats.ts#localBucketKey` is the JS oracle and `emptyBuckets`/`fillBuckets` own the fill.
  MEMBERS: one entry per member with owed > 0 or paid > 0 in range, sorted by owed desc then name; `owed` sums that member's `expense_shares` in range, `paid` sums the expenses they paid. A removed member with activity stays, with `removed: true`.
  COST: aggregate in SQL — never return raw expense rows — over the existing index `idx_expenses_group_live`, at most one batch of 3 statements.
  HELPERS: lib/stats.ts (SSOT, pure, import-safe on the server and in client components) exports `VN_OFFSET_HOURS = 7`, `parseStatsQuery(params, now?)` (→ {period, year, month}, throws 400 VALIDATION in Vietnamese), `statsRangeUtc(period, year, month)` (→ {startIso, endIso} of the local range, null for "all"), `emptyBuckets(period, year, month)`, `fillBuckets(period, year, month, rows)` (`all` sorted from the rows, year/month merged into the zero-filled set with out-of-range keys dropped), `localBucketKey(spentAtIso, period)` (the JS oracle for the SQL's GROUP BY) and `formatCompactVnd(n)` ("350k", "1,2tr", "1tỷ" — for chart axes; lib/format.ts keeps the full "120.000đ" form).
SPLIT RULE: equal split among participants; sort participantMemberIds ascending; base = floor(amount/n); the first (amount mod n) get base+1; shares always sum to amount. Removed members cannot be picked for new expenses (an edit may keep removed members already in that expense). Adding members, presets (create/update/delete/sync) and viewing stay open to every active member; expenses and removals follow PERMISSIONS below.
PERMISSIONS: `lib/permissions.ts` is the SINGLE source (pure, import-safe on the server AND in client components); routes AND pages call it, never a copy of a rule. Every rule is evaluated against the caller's `Viewer`. `isOwner` means `viewer.isOwner` (groups.created_by); the admin account (`isAdmin`) counts as owner-level in every row.
- `canModifyExpense(viewer, expense, members)` — edit/delete an expense iff admin || owner || `expense.createdByUserId === viewer.userId` || the payer member's `userId === viewer.userId` || (`expense.kind === "payment"` and the single share's member has `userId === viewer.userId`, i.e. the receiver). Anyone else → 403 FORBIDDEN.
- `canRecordPayment(viewer, payerMemberId, receiverMemberId)` — recording an expense with `kind: "payment"` iff admin || owner || `viewer.memberId` equals the payer or the receiver. Creating `kind: "expense"` stays open to any active member.
- `canRemoveMember(viewer, target: Member)` → `{ok:true}` | `{ok:false, code, message}`: the owner's own member row is protected from EVERYONE (`OWNER_PROTECTED`, 409 CONFLICT at the route); owner and admin remove anyone else; any other member removes ONLY their own row; everything else `FORBIDDEN` (403). Denials carry a Vietnamese message.
- Open to every active member: adding members, presets (create/update/delete/sync). Viewing stays group-members-only.
LOG: every mutation writes one activity_log row in the SAME D1 batch as the mutation. summary is Vietnamese, e.g. `Hưng đã thêm chi tiêu "Ăn trưa" 120.000đ`. detail: expense.create {after: Expense}, expense.update {before: Expense, after: Expense}, expense.delete {before: Expense}, member.bank {before: BankInfo|null, after: BankInfo|null} with entityType "member" and summary `<actor> đã cập nhật tài khoản ngân hàng của "<name>"` — HISTORICAL ONLY, no longer written (bank info is the user's profile, not a group-scoped change; `LogAction` keeps the value so old rows render), preset.create {after: Preset}, preset.update {before: Preset, after: Preset}, preset.delete {before: Preset}, preset.sync {sourceGroupId, overwrite, added: string[] (names), updated: number, skipped: number} with entityType "group", others null or {member}.
VIETQR: the payment QR is a plain public image URL, no API key and no server call by us: `https://img.vietqr.io/image/{bin}-{accountNo}-compact2.png?amount={vnd}&addInfo={enc}&accountName={enc}`, every variable segment encodeURIComponent-encoded. lib/vietqr.ts (SSOT) exports `VIETQR_BANKS` ({bin, code, shortName, name, logoCode?}[]), `POPULAR_BANK_BINS`, `bankByBin(bin)`, `popularBanks()`, `banksByShortName()`, `matchBank(entry, query)` / `searchBanks(query)` (case- and diacritic-insensitive over shortName, name, code and bin), `bankLogoUrl(entry)` (VietQR's logo CDN, keyed by VietQR's own `logoCode` — which differs from `code`, e.g. VietinBank is ICB — or null when there is no logo; the mapping is static, the app never calls the bank API), `stripDiacritics(text)`, `parseBankInfo(raw)` (400 VALIDATION on a malformed account), `buildVietQrUrl({bin, accountNo, accountName, amount, addInfo})` and `sanitizeTransferNote(text)` (diacritics incl. đ stripped, only [A-Za-z0-9 ] kept, spaces collapsed, max 25 chars). The module is import-safe on the server and in client components. The QR is built from a MEMBER row's `bank`, which is derived from that member's linked user: a friend added by name (no account) has no QR. lib/group-queries.ts owns the derivation (`toBankInfo` reads the three columns, all-or-nothing) and `buildViewer(user, actor)` builds the `Viewer` every group route returns.
PAGES: /login, /register, /groups, /groups/[groupId]/expenses, /groups/[groupId]/expenses/new, /groups/[groupId]/expenses/[expenseId]/edit, /groups/[groupId]/members, /groups/[groupId]/presets, /groups/[groupId]/settle, /groups/[groupId]/log, /admin (admin account only). `/` redirects to /groups; `/groups/[groupId]` redirects to .../expenses. Pages are client components calling the API through lib/api-client.ts.

RATE LIMITS & ABUSE GUARD (every /api route, in this order, all before any per-request DB work; a rejected request costs no D1 rows):
1. IP BAN: a banned address gets 403 FORBIDDEN "Địa chỉ IP của bạn đã bị chặn…" (login and register included). The ban list is read from D1 at most once a minute per isolate and cached in memory, so a lift or a new ban reaches other isolates within ~60s. "unknown" (no address header) is never banned; a failing read fails OPEN.
2. PER-IP THROTTLE: POST /api/auth/login and /api/auth/register 10 requests / 60s; every other /api/* 120 / 60s (Workers Rate Limiting bindings RL_AUTH / RL_API, else an in-memory fixed window per isolate). Over the limit → 429 RATE_LIMITED + `Retry-After`.
3. PER-SESSION WRITE BUDGET: any non-GET/HEAD request that carries a `sid` cookie is also counted per session (sha256 of the cookie): 30 mutations / 60s (binding RL_WRITE, else memory). Over it → 429 RATE_LIMITED, and an `abuse_events` row is recorded (one per account per 10 min per isolate, pruned after 7 days).
4. AUTO IP BAN: when ≥ 3 DIFFERENT accounts record a violation from the same address within 30 minutes, that address is banned for 24 hours (ip_bans.source "auto"). The accounts are only flagged (AdminUser.recentAbuse), never banned automatically: a shared address must not cost an innocent account.
5. SIGN-UP CAP: at most 10 registrations per address per rolling 24h (counted from users.created_ip; 429 RATE_LIMITED).
6. BODY CAP: a JSON body larger than 32 KB → 400 VALIDATION before parsing.
Unknown session tokens are remembered for 60s per isolate so a flood of random cookies costs one D1 read, not one per request. Honest limits: counters are per Cloudflare location/isolate, not global; this is cheap early rejection at the application layer, not L3/L4 DDoS protection (that is Cloudflare's always-on network mitigation in front of the Worker).
CACHING: lib/api-client.ts caches GET responses for 30s, dedupes in-flight GETs and clears the affected entries after a mutation (`fresh: true` bypasses it). The server caches a session lookup per isolate for 30s.
